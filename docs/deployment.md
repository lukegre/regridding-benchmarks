# Deployment and reproduction

The existing Pages site remains `main` → `/docs`. The staged deployment needs a Renku project, durable storage, an image registry and a resource class. Configure unattended Renku credentials only after testing them on the target deployment.

## Image

The Linux x86_64 image pins the micromamba 2.3.3 amd64 manifest. It creates the original Python and compiled environments, installs the hashed DGGS and pyinterp layer, and creates a separate hashed xHEALPixify environment to retain the original NumPy version in the main environment. The original pip and conda locks and the apt Git package leave parts of the build without artifact hashes. JupyterLab has a pinned direct version and separately resolved transitive dependencies.

```sh
REV=$(git rev-parse HEAD)
docker build --platform linux/amd64 --build-arg BENCH_SOURCE_REV="$REV" \
  -f environments/Dockerfile -t regridding-benchmarks:test .
docker run --rm regridding-benchmarks:test /opt/benchmark/source/environments/smoke-image.sh
```

Record the registry's pushed manifest digest, smoke output, source revision, architecture and build logs. Run the smoke again by digest as non-root. The image workflow tests a trusted main revision on native Linux, including DGGS imports and round trips. Set `BENCHMARK_BASE_IMAGE` to override the base by digest, and `BENCHMARK_PUSH_IMAGE=true` to push a tested image to GHCR and report its digest. Update locks through review and repeat the checks after version changes.

The local amd64 image passed non-root interpolation with NumPy 2.5.5 and xarray 2026.9.0, xESMF 0.9.2 with ESMPy 8.9.1, and CDO 2.6.5. The macOS ARM Docker engine's amd64 runtime raised SIGILL while importing the `h3ronpy` wheel, which xdggs imports. The profile reports affected operations as unavailable and retains the import error. The same DGGS cases passed on native macOS ARM. Native Linux validation remains a deployment gate.

The amd64 pilot used local image configuration ID `sha256:1d0eca4dcc5ae49653be7b182aa4e40591445fbb37260e099eac89ee5fe80f76` and temporary verification revision `ba8467b4e5a90130178ae106ee319ec9701e6e2e`. The batch launcher produced and validated 28 smoke samples and 72 standard samples on separate writable mounts. Both bundles could be read and checked against the pinned checkout after the container exited. The pilot series is `linux-emulation-pilot`. Publishable runs need a registry manifest digest and measurements on the designated native resource.

## RenkuLab launchers

1. Create a project linked to this repository; record project namespace and launcher IDs here after provisioning. Create an external environment referencing the same published image by digest. A session launcher needs a web frontend; the image includes JupyterLab. For a session configure the command as `["bash", "/opt/benchmark/source/deploy/renku/session.sh"]`, port `8888`, and default URL `/lab`; set the checkout path in `BENCH_REPO`. The script uses the Renku-injected base URL path. Check the advanced settings against the target installation before launch. Renku runs images as non-root. [Image requirements](https://docs.renkulab.io/en/latest/docs/users/compute/environment/guides/use-your-own-docker-image-for-renku-session/).
2. Create a Job launcher with this external environment, a checkout pinned to the image's full commit SHA, and job command `["bash", "/source/deploy/renku/job.sh"]` (substitute the actual checkout path). Configure `BENCH_REPO` as the checkout path, `BENCH_SOURCE_REV`, `BENCH_IMAGE_DIGEST` (`sha256:…`), `BENCH_RUN_ID`, `BENCH_PROFILE` (smoke or standard), `BENCH_SCRATCH_DIR`, `BENCH_CACHE_DIR`, and `BENCH_OUTPUT_ROOT`. Scratch and cache must be writable, separate from durable output. Mount the latter through an appropriate writable connector, or implement and verify an explicit upload before allowing the job to exit. The script rejects a dirty or mismatched checkout and mismatched image revision. A Job launcher uses an external image or an environment built from code; global environments are not supported for jobs. [Job launcher guide](https://docs.renkulab.io/en/latest/docs/users/compute/job/guides/create-a-job-launcher/).
3. In a session with the same pinned checkout/image and mounts, run the same job script with a new ID. Submit a smoke Job, close the browser, and after completion read and validate its bundle from a separate session. Record peak resource use, choose a resource class, and pilot the full matrix before setting standard or extended limits. [Resource classes](https://docs.renkulab.io/en/latest/docs/users/compute/resource-pools-and-classes/).
4. Confirm supported unattended authentication, renewal, job submission, status polling, and result retrieval on the actual deployment before integrating a scheduler. The [Renku CLI reference](https://docs.renkulab.io/en/latest/docs/users/cli/cli-reference/) documents interactive login and Job commands; it does not prove unattended credentials work for this project.

## CI, candidate retention, and cutover

Pull requests run offline tests. The image workflow builds and smokes a trusted revision. The monthly/manual refresh is disabled unless `BENCHMARK_REFRESH_ENABLED` is `true`; it requires a dedicated self-hosted Linux x64 runner labelled `regridding-benchmark` and `BENCHMARK_IMAGE` pinned by digest. It serializes refreshes and keeps candidates and failed diagnostics as Actions artifacts. Its measurements are labelled `controlled-linux`, distinct from `renkulab`. Configure runner isolation, capacity and artifact retention before enabling. Actions scheduled workflows can be delayed or skipped; monitor execution separately. [Schedule semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

Candidate Actions artifacts are temporary. The **Publish or roll back an edition** workflow stores complete site snapshots in GitHub Release assets under `benchmark-edition-<run-id>`. Before using it, enable immutable releases in the repository and verify the setting, then set `BENCHMARK_IMMUTABLE_RELEASES=true`; See [GitHub release integrity](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/verify-release-integrity). Confirm adequate asset limits, retention, access and dataset redistribution rights. Configure Pages to use GitHub Actions only at cutover. The workflow is restricted to `main` and serializes deployments. The GitHub Pages environment can apply the repository's existing protection rules. [Pages workflow guide](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

For manual publication, supply the successful candidate workflow run ID and attempt, and the latest `benchmark-edition-*` release tag (empty only at the first cutover). The workflow verifies the release attestation and archived snapshot checksum, restores its editions, validates the candidate for publication, builds the site with historical editions and legacy paths, creates a new release with a complete site snapshot, and deploys it. Automatic publication is opt-in: set `BENCHMARK_AUTO_PUBLISH=true` only after the full staging and rollback rehearsal. The workflow consumes only successful scheduled or manually dispatched trusted main refreshes and checks their recorded roster against that revision; it does not execute candidate checkout scripts. The publication validator requires image provenance and a complete standard or extended profile; smoke timings must not become performance editions. The release is created before deployment, so a failed deployment may leave an unused release, but it does not advance Pages. Rerun using a new candidate ID if necessary. Actions artifact retention must cover the review interval.

For rollback, dispatch the workflow with operation `rollback` and the target edition release tag. It verifies and deploys that exact archived site snapshot. A later publication must use the most recent release tag, so it restores all editions even after a rollback. Rehearse a deliberately failed validation and cancellation, confirm the previously deployed site remains available, then rehearse rollback and verify old URLs and edition checksums. No such rehearsal has been performed. Review archive contents, citation metadata and reuse terms before public release; access to input data does not imply redistribution permission.
